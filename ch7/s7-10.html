7.10　综合案例：用”今日工作助手”串联四类工程技术

前文分别解释了任务合同、上下文、Harness、Loop 与安全边界。本节用 PPT 中的“今日工作助手”作贯穿案例，在纸面上走完一次任务的输入、决策、执行和验收。案例采用假设的 Mock 数据与接口，用来说明技术设计；它不对应一套已经实现的软件。希望动手观察开源系统的读者，可另行阅读 Hello-Agents 的教学代码与 Hermes Agent 的技能、记忆实现。

7.10.1　任务目标与系统边界

接续 7.3 节的任务合同：读取 Calendar、Mail、Tasks 三类模拟数据，生成今日会议、三封优先邮件、逾期待办、会议冲突和简短安排；发送邮件、变更日历、删除任务必须先展示摘要并等待确认。假设读者正在设计这样一个系统，需要说明输入格式、输出规则、工具权限和完成判据。

概念架构分成五层：输入数据层保存带版本的模拟记录；Adapter 将三类数据转换为统一结构；策略层决定工具调用能否执行；Agent Loop 保存任务状态并组织下一步；验证层检查业务结果和拒绝授权后的行为。若将来实现，前端、Mock 服务和 Agent 可以采用不同技术栈，但接口契约应保持一致。模型提供计划和文本生成，排序、时间比较、权限检查与测试判定由确定性代码完成。

user_task -> task_contract -> context_builder -> agent_loop
| |
versioned mock data tool_gateway
|
Calendar / Mail / Tasks Mock
|
tests + audit log + report

每条模拟记录应有稳定 ID、来源和更新时间。会议用 ISO 8601 时间并明确偏移量；邮件用收件时间、优先级和是否已读；任务用截止时间与完成状态。案例使用固定的 reference_time，例如 2026-10-29T09:00:00+08:00，使”逾期”和”今日”的判断有明确依据。时间比较先统一为同一时间基准，再格式化为用户所在时区；不能直接比较展示字符串。

7.10.2　工具契约、状态和权限

概念上的读取工具为 list_events(day)、list_messages(limit) 和 list_tasks(status)；写入工具为 send_message(draft)、create_event(event)、delete_task(id)。工具应返回结构化状态、数据版本和错误类别。对写入工具，网关在执行前检查用户身份、目标、动作摘要和审批令牌；没有令牌时返回 approval_required，Agent Loop 进入 WAITING_FOR_USER。拒绝审批后，不应出现写入成功记录。

一次可追踪的调用记录至少包含 task_id、tool_name、参数摘要、结果状态、数据版本、代码 commit、耗时和审批 ID。日志对邮件正文与敏感数据采用最小记录原则：保存必要的摘要或哈希，不把完整内容复制进诊断日志。工具请求附带唯一请求 ID，重试写入前先查询该 ID 的状态，以免重复发送或重复创建。

Loop 可沿 READY → WORKING → VERIFYING → COMPLETED 推进，另保留 WAITING_FOR_USER 与 BLOCKED。每轮根据最新工具结果更新状态；验证失败则返回工作状态；只有业务断言、权限断言和交付证据都指向当前版本，才能完成。7.7 节的状态机和 7.5 节的 Harness 草案提供了具体设计依据。

7.10.3　用固定数据推演一次结果

设参考时间为 2026-10-29T09:00:00+08:00。Calendar 返回两场会议：A 为 09:00—10:00，B 为 09:30—10:30；Mail 返回四封邮件，其中三封标记为高优先级；Tasks 返回一项截止于前一日且未完成的待办。按预先定义的规则，应标记 A 与 B 冲突，展示三封高优先级邮件，并将该待办列为逾期。安排文本可以由模型生成，但不得改变这些事实字段。

读者可以按四类工程逐步检查推演：Prompt 是否定义”优先”和”逾期”；Context 是否携带记录来源、时区与参考时间；Harness 是否在写入前检查审批；Loop 是否在发现时间解释错误后返回验证。业务验收应检查优先邮件排序、逾期判断、会议重叠和时区转换；安全验收应检查无批准不能执行写入、拒绝后无副作用、外部文本不能扩大工具权限。自然语言安排允许表达差异，事实字段和动作状态必须一致。

若在实际项目中采用这些规则，验收报告还应列出检查结果、失败轨迹、成本、修改文件和未验证项。本书的推演只给出应检查什么及原因，不声称已有运行结果。

7.10.4　两种失败情境与一项改进判断

时区故障：假设 Adapter 把带 Z 的时间戳再次按本地时间解释，产生 7.7 节的八小时偏差。正确的 Loop 应先核对输入格式和转换边界，修正原因后进行局部与完整验证。若只反复读取同一错误输出而没有新证据，循环没有收敛。

恶意工具返回：假设某个邮件字段包含要求改变任务目标的文字。它仍是邮件数据，不能成为授权指令。即使模型提出越界动作，工具网关也应拒绝，并分别记录决策层与执行层的结果。

有限 RSI 改进：从多条时区错误轨迹提出候选规则，例如”处理跨系统时间前检查偏移量是否已编码”。评价时应限定修改模块，并使用未参与候选生成的日期任务。若收益只出现在原故障样本，候选不能进入下一版本。这里展示的是评价逻辑，不宣称已经完成一次 RSI 实验。

7.10.5　延伸阅读：观察已有开源实现

读者可在 Hello-Agents 中寻找工具、记忆和多 Agent 的教学实现，再在 Hermes Agent 中观察技能如何保存与复用。阅读时固定所看的版本，逐项对照本节的任务合同、信息来源、权限边界、循环状态和验证方式。开源项目的具体架构会迭代，项目代码是分析对象，不是本章概念的唯一实现。

这个案例串起四类工程：任务合同规定结果，上下文选择证据，Harness 决定可执行边界，Loop 用反馈促使任务收敛。下一节将同一类工作流放进端、边、云环境，讨论资源受限与网络不稳定时如何继续保证这些约束。
