7.3　Prompt Engineering：把需求写成任务合同

用户习惯用结果描述需求：“做一个今日工作助手”“修复提醒时间”“优化查询接口”。人听得懂大致方向，Agent 却无法据此判断该读哪个项目、能改什么、何时停下。本节说明 Coding Agent 中的提示工程不是把话说得更漂亮，而是把意图写成一份任务合同：写清目标、事实、边界、证据和交付格式，让 Agent 能开始工作，也让人能依据独立证据检查它是否做完。本节还区分两类约束：写在文字里的“提醒”和由执行系统落实的“强制”。

7.3.1　任务合同回答五个问题

任务合同（task contract）是事先写明“做什么、怎样算做完”的约定。它要回答五个问题：要得到什么？依据什么？不能越过什么？拿什么证明？最后交付什么？对应的五项内容见表 7-5。五项不是固定的“咒语”，作用是保证每个关键判断都有人负责，不留给 Agent 去猜。任务合同不是提示之外的另一份文件：它通常就写在给 Agent 的任务提示里，长期适用的部分则写进项目说明文件，可以看作提示工程在 Coding Agent 场景下的具体形态。

表 7-5　任务合同的五项内容

要素 应写清的内容 缺失时的典型后果
目标 用户最终能看到或使用的结果 只做了看似相关的改动，需求并未完成
事实 仓库位置、现有接口、故障现象、可信资料 猜测数据结构、命令或技术栈
边界 可改范围、禁止的动作、需要人确认的动作 无意扩大修改范围，或触发外部副作用
证据 测试、构建、指标、截图或人工验收点 用“我已完成”的文字代替检查
交付 代码差异、测试结果、未完成项和风险怎样呈现 读者无法复核改动，也无法接手下一步

目标与证据要配对。目标是“降低查询延迟”，就要指定测量对象、统计口径和阈值，例如“在同一测试数据集上，订单查询接口的 P95 延迟低于 300 ms”。这里的 P95 指第 95 百分位数：把所有请求的延迟从小到大排列，位于 95% 分位处的那个值，约有 5% 的请求比它更慢，用来刻画“慢的那一头”（尾部延迟），比平均值更能反映用户感受到的卡顿。“统计口径”则要说清测的是什么，例如同一数据集、预热之后、只计服务端耗时。目标是“修复会议冲突提醒”，就要说明什么样的输入应当产生冲突标记，并让测试或可复现的操作承担证明。测试命令只是检查手段，它是否真的覆盖了业务目标，还要核对断言和测试数据。

事实不等于把资料全粘进来。合同只需指出可靠的起点，例如“先读 README、package.json 和三个 Adapter 的接口”；哪些内容在某一轮进入模型，是第 7.4 节的问题。把“请查看仓库”写进合同，是在指明取证方向；Agent 实际读到了什么，要以工具返回的结果为准。

7.3.2　描述结果，不遥控步骤

提示写得过短会留下歧义，写得过细会带来另一种问题：人预先指定的步骤可能与仓库事实不符。例如不了解现有数据层，就命令 Agent“新建一个邮件数据库表”，结果绕开了项目已有的 Mock Adapter。更稳妥的写法是规定可观察的行为和不能破坏的条件，让 Agent 读完项目后自己选择实现路径。

对比两种写法。“优化一下订单接口”只给了方向；“将订单查询接口的 P95 延迟降到 300 ms 以下，保持现有 API 兼容；修改后运行基准测试和回归测试，列出改动文件、测试结果和仍存在的风险”则依次给出了五样东西：结果（降延迟）、参考（现有 API）、量化目标（300 ms）、验证方式（基准与回归测试）、输出格式（文件、结果、风险）。它没有规定改哪个函数、用不用缓存，这些留给 Agent 根据仓库决定。

在今日工作助手里，“做一个功能完善的智能助手”是模糊的说法；可执行的目标是“在现有 Next.js + TypeScript 项目中，首页展示今日会议、三封高优先级邮件和逾期待办，标记时间重叠的会议，生成 150～200 字的今日安排”。它仍然没规定组件怎样拆、状态管理用什么库，却已经给出了可以检查的结果。

任务较大时，可以把合同继续拆成一串工件：规格说明写行为，计划写拟改的模块，任务表列出可以独立检查的工作项，然后再改代码。GitHub 开源的 Spec Kit 采用这种流程：先为项目写一次“宪章”（constitution，项目级的原则），然后依次执行 Specify（写规格）→ Plan（写技术计划）→ Tasks（拆任务）→ Implement（实现）→ Converge（对照规格、计划和任务检查代码，发现缺口就追加任务，直到收敛），中间还可以插入澄清、分析等可选的质量检查步骤[13]。值得借鉴的是在意图和实现之间留下可审阅的中间结果；小修复不必机械地套完整流程。

7.3.3　把“完成”写成可检查的条件

合同里最重要的一行往往是完成条件。只写“直到做好为止”不行：Agent 不知道“好”由谁判定，也可能在测试失败时给出乐观的总结。完成条件最好同时覆盖功能、回归、运行和交付四类证据。针对今日工作助手，可以先写出表 7-6 这样的验收表，它描述业务预期，不依赖具体的测试框架。

表 7-6　今日工作助手的验收表

规则 输入或操作 可观察的预期
会议排序 两场开始时间不同、原始顺序颠倒的会议 页面按开始时间排列
邮件筛选 多于三封、优先级不同的邮件 只展示优先级最高的三封
待办逾期 未完成且截止时间早于当前时间的待办 标记为逾期；已完成的不标记
会议冲突 两场时间区间有交集的会议 标出冲突，并指出是哪两场
拒绝写入 用户拒绝发送邮件或写日历 外部写入工具没有被执行
简报长度 生成今日安排 字数在 150～200 之间，所含事实与上面各项一致

验收表还要落实为可运行的检查：为排序、邮件筛选、逾期、冲突和简报长度写单元测试；为页面显示做构建或界面检查；为“拒绝后不写入”检查工具调用记录。代码检查（lint）、测试（test）、构建（build）全部通过以后，仍要看最终的代码差异，确认没有顺手改动无关模块。由此形成一条证据链：运行检查 → 读取结果 → 失败则修正后重跑 → 输出差异、测试结果和风险。某项检查无法运行时，报告必须写明原因、做了什么替代检查、哪些结论还不能证实。

完成条件最好在任务开始前确定。否则 Agent 可能在实现之后挑选容易通过的检查，形成“先有答案、再找证据”。OpenAI 为 Codex 提供的 Goals 功能（Codex 0.128.0 起支持，用 /goal 命令设置、暂停、恢复和清除）把目标、验证依据、约束和受阻时的停止条件作为线程级的持久目标保存，作用正是让长任务的终点不随对话推进而悄悄改变[4]。

7.3.4　提醒与强制：边界写在哪里

边界可以写进提示，例如“不要接入真实邮箱”“发邮件前先给用户看摘要”。这能帮 Agent 作出正确选择，但文字本身限制不了终端命令或外部 API：模型可能没注意到这句话，也可能被别的文本说服。因此要把约束分成两类（表 7-7）。

表 7-7　“提醒”与“强制”两类约束

对比项 提醒（写给模型看） 强制（由执行系统落实）
载体 任务合同、项目说明文件（AGENTS.md、CLAUDE.md） 权限规则、沙箱、Hook、CI 门禁
由谁执行 模型理解后自行遵守 模型之外的程序，在动作执行前或后检查
模型出错时 约束失效 越界动作仍被阻止或被检出
适合写什么 偏好、惯例、推荐做法、为什么这样做 不允许有例外的规则：密钥、生产数据、对外发送
例子 “优先复用现有组件”“改完先跑相关测试” 读密钥目录一律拒绝；发邮件必须经用户批准

辨析

在提示里写了“不能发邮件”，不等于 Agent 发不了邮件。只要发送工具仍然可以直接调用，风险就还在。规则如果必须无条件生效，就要落到执行层：关闭这个工具，或把它设为“调用前必须批准”。Claude Code 等产品正是为此在项目说明文件之外，另外提供了权限规则、沙箱和 Hook 这些由程序执行的机制[2]。提醒的价值在于让模型少犯错，强制的价值在于模型犯了错也不造成损害，两者互补。

写边界时按动作分类，而不是笼统地要求“注意安全”。以本章案例为例：读取项目中的 Mock 数据可以自动进行；在指定工作区修改文件并留下差异可以自动进行；调用真实的邮件或日历写接口必须暂停等待确认；读取密钥目录、删除生产数据由权限规则直接拒绝。这套分类只是教学项目的设计，真实项目要按数据敏感度和组织政策决定。

“需要确认”还要说清确认的对象。用户批准发邮件时，至少应看到收件人、主题和正文摘要；批准改日历时，应看到事件、时间、时区和参与人。否则用户只是批准了一个模糊的动作名称。第 7.5 节会说明怎样把这些要求写进工具接口和审批流程。

7.3.5　一份可直接使用的任务合同

把前面五项合在一起，得到下面的模板。方括号里的内容由具体项目填写；结构比字数重要。

目标：在[项目/工作区]完成[可观察的结果]。
事实：先读取[入口文件、现有接口或故障证据]；以当前代码和工具结果为准。
边界：只改[允许范围]；保留[兼容性或既有行为]；[外部写入]前暂停并请求确认。
证据：运行[与功能直接对应的检查]，再运行[回归/构建检查]；查看最终 Diff。
交付：列出修改文件、检查命令及结果、未执行项、已知限制。
受阻时：说明已查证的事实、阻塞原因和继续所需信息，不把未验证的结果写成已完成。

套用到今日工作助手，一份完整的合同是：

请在当前 Next.js + TypeScript 仓库中完成“今日工作助手”首页。开始前先读 README、AGENTS.md、package.json 和 Calendar、Mail、Tasks 三个 Mock Adapter 的接口，说明你对任务的理解、拟修改的文件和验证命令。首页展示今日会议、优先级最高的三封邮件、逾期待办和会议冲突，并生成 150～200 字的今日安排。只使用 Mock 数据，不接入真实账号；发送邮件、创建或取消会议、删除任务之前，必须展示动作摘要并等待确认。为排序、逾期、冲突和“拒绝确认后不写入”补充测试；运行项目已有的 lint、test、build 命令，并检查最终 Diff。最后列出改动的文件、实际运行的检查及结果、页面截图和仍未完成的部分。若项目接口或测试环境与上述要求冲突，先报告冲突和可选的处理方式。

这份合同没有规定“必须写哪几个组件”，但让 Agent 知道从哪里开始、在哪里停下、拿什么证明。如果开工后发现项目只有部分 Adapter，合同不应被默默改写；Agent 应报告与现状不符的事实，再根据用户的决定调整范围。

7.3.6　常见失效及其修正

目标只有形容词　 “界面高级”“功能完善”“性能更好”可以指示方向，却无法判断完成。应补上页面状态、响应时间、兼容性等可检验的结果。

把计划当成结果　 “先查三个文件、再写两个组件、最后跑测试”描述的是步骤，没说最终行为。计划可以随仓库事实改变，验收标准则应保持稳定，除非用户明确调整需求。

只要求测试通过　 旧测试全部通过，可能只是因为新功能根本没被覆盖。应先从业务规则推出边界条件，再指定相关检查。

权限只停留在文字里　 见上文辨析：应在 Harness 中关闭工具或设为必须批准，审批结果再返回循环，影响下一步。

不允许诚实地停下　 依赖缺失、测试环境不可用、需要人决定的业务规则，并不都能由 Agent 自己解决。合同应允许它报告受阻：说明已确认的事实、试过的办法、还没完成的检查和最小的待决问题。这比一句没有证据的“已经修复”有用得多。

本节要点

  • 任务合同 = 目标 + 事实 + 边界 + 证据 + 交付；目标与证据要配对，完成条件在开工前写定。

  • 描述结果和约束，不遥控实现步骤；大任务可拆成规格、计划、任务等可审阅的中间工件。

  • 提醒写在合同里，强制落在执行层；不容例外的规则必须由权限、沙箱或门禁执行。
