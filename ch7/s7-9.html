7.9　安全与可信交付：把信任边界放在工具之前

Coding Agent 会读仓库、网页、Issue、工具结果和其他 Agent 的消息，又能执行命令、改代码、装依赖、调外部服务。它的风险不只是模型“说错话”，更在于低信任的内容影响了高权限的动作：文件里的一段文字被当成上级指令，一份工具结果改变了执行计划，一项依赖变更把恶意逻辑带进了交付物。本节沿着“内容进入 → 模型决策 → 工具执行 → 产物交付”这条链，分析提示注入、后门、工具投毒和记忆污染分别从哪里进入，在哪里拦截。结论是：防护必须放在链上的多个节点，靠模型“不上当”是不够的；可信交付是一条可追溯的约束链。

7.9.1　保护对象与信任边界

本章教学项目涉及仓库代码、用户日程和邮件 Mock 服务；真实系统还可能接触源代码机密、API 凭据、客户数据、发布令牌和生产环境。用户的合法任务和授权决定 Agent 的目标；仓库文件、外部网页、检索片段、MCP 工具的描述与结果、A2A 远端的消息，都可能受第三方影响，不能因为进入了上下文就获得指挥权。表 7-17 是一份简化的威胁模型。

表 7-17　Coding Agent 的主要入口、风险与边界

入口或资产 典型风险 必须守住的边界
README、Issue、网页、邮件正文 间接提示注入改变任务目标 外部内容只作为待分析的数据
MCP 工具描述与返回值 工具投毒、诱导调用其他工具 工具定义须审核；结果不能授予新权限
A2A 远端的消息与产物 伪造“已完成”、索要额外凭据 委托范围、身份、交付版本独立校验
依赖、脚本、技能文件 隐藏后门或危险的安装步骤 来源、差异、执行行为和构建链可审计
长期记忆与 RSI 候选 错误规则被持久化、跨任务污染 写入审批、来源记录、有效期与回滚

攻击路径通常是：攻击者可控的内容 → Agent 上下文 → 模型决策 → 高权限工具 → 数据或系统被改变。开放式全球应用安全项目（Open Worldwide Application Security Project，OWASP，原名 Open Web Application Security Project）在 2025 年版大模型应用十大风险中把提示注入列为第一位（LLM01）[23]；它在 2025 年 12 月发布的智能体应用十大风险（2026 年版）中，前几项依次是智能体目标劫持、工具滥用、身份与权限滥用、智能体供应链漏洞[24]。只在提示里写“不要受骗”，代替不了工具级的权限控制：模型是否遵守一句自然语言指令无法事先验证，攻击文字还可以改写、编码、拆散在多处。

7.9.2　间接提示注入：数据怎样越过指令边界

用户请 Agent 修一个错误，Agent 读仓库文档是正常步骤。如果文档里出现要它改变目标、忽略原任务、或把资料发往外部服务的文字，这段文字仍然只是仓库内容，不是用户授权。间接提示注入（indirect prompt injection）就是让低信任来源中“像指令的文本”越过这条边界：攻击者不直接与模型对话，而是把文字放在模型会读到的网页、文件或工具结果里。后果可能是敏感信息泄露、未经授权的工具调用，等等[23]。

工程上分三层处理：

  • 输入层：为每段内容保存来源、读取时间、仓库提交号和信任级别；检索摘要要能指回原文位置，避免摘要把“文档声称”改写成“系统要求”。

  • 决策层：核对当前动作是否来自用户的任务合同；外部材料提出的新目标只记为待审信息。

  • 执行层：工具网关按身份、路径、网络目的地和动作类型重新授权；即使模型错误地提出调用，越界动作也被拒绝并留下日志。

给不可信文本加引号或标注来源，有助于模型区分，但不是可靠的唯一防线。真正的保障在执行层：它不依赖模型判断正确。

7.9.3　后门、依赖与技能：正常任务也可能带入恶意代码

辨析

提示注入与软件后门发生在不同阶段。提示注入在阅读阶段改变 Agent 的决策；后门则是已经进入代码、依赖或技能之后，在特定条件下才触发的未授权行为。二者可以串联：恶意文档诱导 Agent 安装某个包，包里的代码再形成后门。后门可能藏在看似合理的功能改动里，只在特殊输入或环境下触发；普通功能测试没覆盖触发条件，测试通过也不等于安全。

防护要覆盖从选型到交付的整条变更链。新增依赖要核对包名、来源、版本和锁文件的实际变化，审查安装脚本及其权限；生成的代码要检查有没有与任务无关的文件、外部连接、凭据读取和异常的条件分支；技能或插件要同时检查说明文字和可执行脚本，安装后限制其工作目录、网络和凭据。对高风险变更，静态分析、依赖漏洞扫描、隔离环境中的动态测试和人工代码审查各提供不同的证据，任何一项都不足以单独宣称“没有后门”。

技能本身也可以成为攻击面。ICML 2026 上的 SkillTrojan 研究针对基于技能的 Agent 系统构造后门：恶意逻辑藏在技能的实现和技能之间的组合中，只有特定触发条件出现时才执行。作者公开了 3000 多个带后门的技能样本，在一项电子病历 SQL 查询任务上报告的攻击成功率最高达 97.2%[25]。这提示我们：只审查模型的输入和最终回答是不够的，被加载的技能同样要审查。

7.9.4　MCP、A2A 与记忆：连接越多，授权越要具体

MCP Server 提供的工具名称、说明、参数描述和返回值都可能被恶意服务操纵。Host 若把 Server 的描述直接当成可信的操作建议，一个 Server 甚至可能左右模型对其他工具的选择，这类攻击称为工具投毒（tool poisoning）：恶意 Server 在工具名称、说明或参数描述里藏进诱导性文字，这些文字随工具描述进入上下文，使模型偏向调用或信任它，或者在调用别的工具时附带泄露数据。应对办法：接入时固定并审核 Server 的身份、版本和工具清单；运行时对每次调用做参数校验、最小权限授权、目的地限制和日志记录；工具定义一旦变化就重新评估，而不是沿用旧的批准。OWASP 为此发布了两份实践指南：2025 年 11 月的第三方 MCP 服务器安全使用速查表[26]，和 2026 年 2 月的 MCP 服务器安全开发指南[27]。

A2A 委托面对更长的信任链。远端 Agent 可以报告状态、交付产物，却不能替父任务批准发信、部署或访问本地密钥。请求方要验证远端的身份、任务编号、输入提交号、输出内容和权限范围；远端要求更多资料或权限时，回到父任务的授权流程。多个 Agent 一致同意某个动作，也不会让这个动作自动变得合法。

长期记忆会把一次污染变成跨任务的风险：把某个外部页面里的主张存成“以后总是这样做”，后续任务就会反复受影响。记忆条目应保存来源、创建者、适用范围、依据和失效条件；影响大的规则经审查后才能升级为全局技能；删除和回滚要像代码版本一样可操作。RSI 候选受同样约束：不能借“自我改进”把未经批准的工具权限或不可信的记忆写成新的默认策略。

7.9.5　可信交付需要多道相互独立的门禁

把安全控制对应到开发流水线的各个阶段，而不是全压在最后一次审查上（表 7-18）。

表 7-18　开发流水线各阶段的安全控制

阶段 可执行的控制 留下的证据
接收任务与资料 固定用户的任务合同；标记外部内容的来源 任务编号、输入版本、来源记录
连接工具与环境 最小权限、沙箱、凭据按需发放、网络限制 授权策略与工具调用日志
修改代码与依赖 限定路径；审查差异、锁文件和脚本 提交号、依赖清单、审查记录
验证行为 单元与回归测试、依赖扫描、针对性安全测试 与当前提交绑定的 CI 结果
对外交付 高风险动作由人审批；构建产物签名并记录来源 审批记录、构建日志、产物哈希

这些门禁各管一种失败：沙箱限制工具能接触什么，权限策略决定允许它做什么，测试和扫描检查产物的行为，审查判断变更是否符合任务，来源记录帮助事后追溯。发布、发送真实邮件、变更生产权限等高影响动作，应由独立的系统或人批准；模型生成的“已获批准”字样不能当作授权凭据。自动化流水线还要保证测试、审查和最终交付指向同一个代码版本。

7.9.6　数据水印与溯源：能提供线索，不能代替访问控制

数据水印有多种含义。对文本、图片等内容，水印是在内容中嵌入可检测的信号，用于辅助识别来源或追踪传播；对内部测试数据，也可以放入受控的标记，观察是否发生了非预期的外流。水印提供的是检测或归因的线索：检测不到水印不证明内容从未出现过，检测到了也不能直接说明是谁、在何种权限下泄露的。复制、改写、裁剪、格式转换和检测误差都会影响结果，水印还可能被有意去除或伪造。

内容溯源与水印不同。内容来源与真实性联盟（Coalition for Content Provenance and Authenticity，C2PA）制定的规范把内容的创作和编辑过程写成一份清单，以数字签名与内容绑定，面向用户的名称叫“内容凭证”（Content Credentials）；有的实现还借助水印或指纹，找回被剥离的清单。截至 2026 年 11 月，其规范最新版本为 2.5[28]。签名能验证特定声明及其与内容的绑定关系，但不能保证声明覆盖了全部真实历史，也阻止不了内容被滥用。

辨析

水印、溯源和访问控制回答的是不同问题。水印回答“这份内容可能从哪里来”，溯源回答“这份内容或这个软件包是经过怎样的过程产生的”，访问控制回答“谁有权做这件事”。在 Coding Agent 的软件交付中，更直接的溯源对象是代码与构建链：源提交、依赖锁文件、测试环境、构建步骤、产物哈希与签名、审批记录。它们帮助事后调查，却都不能取代最小权限、隔离执行、代码审查和运行时监控。

7.9.7　怎样验证安全控制确实有效

安全评估不能只问“Agent 最后完成任务没有”。应准备与真实仓库形态相近、但不含真实秘密的测试资料，分别放入：普通说明、带诱导文字的外部文档、被篡改的工具描述、被污染的记忆条目、含可疑依赖变化的提交。记录三类结果：合法任务能否完成；越权动作是否被拦住；误报是否让正常任务无法推进。发现过的失败要变成回归用例，并固定 Agent、工具和策略的版本，以便比较修复前后的行为。

如果一次测试中模型产生了危险意图，但工具网关拒绝了执行，应分别记录“模型判断失败”和“执行边界成功”，不要混成一个成功率。反过来，模型这次没有上当，也不能推出边界足够安全，还要验证在模型失误时，权限拒绝、沙箱和审计照样起作用。安全性最终体现为：在错误输入和错误判断下，系统仍把影响限制在授权范围之内。

本节要点

  • 风险的本质是低信任内容影响高权限动作；防护分布在输入、决策、执行、交付多个节点。

  • 提示注入改变决策，后门潜伏在代码、依赖和技能里；工具投毒和记忆污染会把一次攻击扩散开。

  • 水印提供线索，溯源记录过程，访问控制决定权限，三者不能互相替代。
