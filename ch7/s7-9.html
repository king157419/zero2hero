7.9　安全与可信交付：把信任边界放在工具之前

Coding Agent 会读取仓库、网页、Issue、工具结果和其他 Agent 的消息，并可能执行命令、修改代码、安装依赖或调用外部服务。风险不只在模型”说错话”，还在低信任内容影响高权限动作：一个文件中的文本被当成上级指令，一份工具结果改变了执行计划，一项依赖变更把恶意逻辑带进交付物。因此，安全设计应从数据进入的位置一路追踪到实际动作和最终产物。

7.9.1　先明确保护对象与信任边界

本章的教学项目涉及仓库代码、用户日程和邮件 Mock 服务；真实系统还可能接触源代码机密、API 凭据、客户数据、发布令牌及生产环境。用户的合法任务和授权决定 Agent 的目标；仓库文件、外部页面、检索片段、MCP 工具描述与结果、A2A 远端消息都可能由第三方影响，不能仅因进入上下文就获得指挥权。

入口或资产 典型风险 必须守住的边界
README、Issue、网页、邮件正文 间接提示注入改变任务目标 外部内容只作为待分析数据
MCP 工具说明与返回值 工具投毒、跨工具诱导 工具定义需审核；结果不能授予新权限
A2A 远端 Agent 的 Message / Artifact 伪造完成、要求额外凭据 委托范围、身份和交付版本独立校验
依赖、脚本、技能文件 隐藏后门或危险安装步骤 来源、Diff、执行行为和构建链可审计
长期记忆和 RSI 候选 错误规则持久化、跨任务污染 写入审批、来源记录、有效期与回滚

这个表是一份简化威胁模型。攻击路径常表现为”攻击者可控制的内容 → Agent 上下文 → 模型决策 → 高权限工具 → 数据或系统变化”。防护要放在路径中的多个节点；只在提示词里写”不要受骗”，无法替代工具级权限控制。OWASP LLM01 提示注入

7.9.2　间接提示注入：数据怎样越过指令边界

用户请 Agent 修复一个错误，Agent 读取仓库文档是正常步骤。若文档中出现要求它改变目标、忽略原任务或向外部服务传送资料的文字，这段文字仍是仓库内容，不是用户授权。间接提示注入的本质就是让低信任来源中的指令样式文本越过这条边界。OWASP把网页、文件等外部来源引发的行为偏转归为间接提示注入，并指出它可能造成敏感信息披露、未经授权的工具调用等后果。

工程处理可以分三层。输入层保存来源、读取时间、仓库 commit 和信任级别；检索摘要要带回原文位置，避免摘要把”文档声称”改写为”系统要求”。决策层核对当前动作是否来自用户任务合同，遇到外部材料提出的新目标时只记录为待审信息。执行层由工具网关按身份、路径、网络目的地和动作类型重新授权；即使模型错误地提出调用，越界动作也应被拒绝并留下日志。把不可信文本包进引号或标注来源有助于模型区分，但不是可靠的唯一防线。

7.9.3　后门、依赖与技能：正常任务也可能带入恶意代码

提示注入试图在阅读阶段改变 Agent 决策；软件后门则是进入代码、依赖或技能之后，在特定条件下产生未经授权的行为。两者可能串联：恶意文档诱导 Agent 安装某个包，包中的代码再形成后门。后门也可能藏在看似合理的功能改动里，只有在特殊输入或环境条件下触发；普通功能测试未覆盖触发条件时，不等于安全。

防护应覆盖从选型到交付的整个变更链。新增依赖要核对包名、来源、版本和锁文件的实际变化，审查安装脚本及其权限；生成的代码要检查与任务无关的文件、外部连接、凭据读取和异常条件分支；技能或插件要检查说明文字与可执行实现，安装后限制工作目录、网络和凭据。对高风险变更，静态分析、依赖漏洞扫描、隔离环境中的动态测试和人工代码审查各提供不同证据，不能单独宣称”已无后门”。2026 年 ICML 的 SkillTrojan 论文展示了技能实现与技能组合本身可成为后门攻击面，提示我们不能只审查模型输入和最终回答。

7.9.4　MCP、A2A 与记忆：连接越多，授权越要具体

MCP Server 提供工具、资源和提示模板，但工具名称、说明、参数 Schema 与返回值都可能被恶意服务影响。若 Host 把 Server 的描述直接当成可信操作建议，一个 Server 甚至可能影响对其他工具的选择。应在接入时固定并审核 Server 身份、版本和工具清单；运行时对每次调用做参数校验、最小权限授权、目的地限制和日志记录；工具定义发生变化时重新评估，而不是沿用旧批准。OWASP MCP 安全指南

A2A 委托面临相似但更长的信任链。远端 Agent 可以报告状态和交付 Artifact，却不能替父任务批准发信、部署或访问本地密钥。请求方要验证远端身份、Task ID、输入 commit、输出内容与权限范围；远端要求增加资料或权限时，应回到父任务的授权流程。多 Agent 一致同意某个动作，也不自动增加该动作的合法性。

长期记忆让单次污染变成跨任务风险。把一次外部页面中的主张存成”以后总是这样做”的规则，会让后续任务重复受影响。记忆条目应保存来源、创建者、适用范围、置信依据和失效条件；高影响规则经审查后才可升级为全局技能；删除和回滚应像代码版本一样可操作。RSI 候选也受同样约束：不能通过”自我改进”把未经批准的工具权限或不可信记忆写成新的默认策略。OWASP AI Agent 安全指南

7.9.5　可信交付需要多道相互独立的门禁

可把安全控制对应到开发流水线，而不是压在最后一次审查上。

阶段 可执行控制 留下的证据
接收任务与资料 固定用户任务合同；标记外部内容来源 任务 ID、输入版本、来源记录
连接工具与环境 最小权限、沙箱、凭据按需发放、网络限制 授权策略与工具调用日志
修改代码与依赖 限定路径；审查 Diff、锁文件和脚本 commit、依赖清单、审查记录
验证行为 单元与回归测试、依赖扫描、针对性安全测试 与当前 commit 绑定的 CI 结果
对外交付 人审高风险动作；构建产物签名与来源记录 审批、构建日志、产物哈希

这些门禁各自处理不同失败。沙箱限制工具能接触什么；权限策略决定它被允许做什么；测试和扫描检查产物行为；审查判断变更是否符合任务；来源记录帮助事后追溯。对于发布、发送真实邮件、变更生产权限等高影响动作，应由独立系统或人批准，不能把模型生成的”已获批准”当成授权凭据。对自动化流水线，还应确保测试、审查和最终交付指向同一代码版本。

7.9.6　数据水印与溯源：能提供线索，不能代替访问控制

“数据水印”有多种含义。对文本、图片等内容，水印是在内容中嵌入可检测信号，用于辅助识别来源或追踪传播；对内部测试数据，也可使用受控标记观察是否发生非预期外流。它们通常提供的是检测或归因线索：检测不到水印不证明内容从未出现过，检测到也不直接说明是谁在何种权限下泄露。复制、改写、裁剪、格式转换或检测误差都可能影响结果，具体可靠性依赖算法与场景。

内容溯源与水印也不同。C2PA 的 Content Credentials 通过清单、签名与内容绑定记录创作或编辑过程；某些实现还使用水印或指纹帮助找回被剥离的清单。签名能验证特定声明及其绑定关系，不能保证声明覆盖了全部真实历史，也不能阻止内容被滥用。C2PA 规范、C2PA 实施建议

在 Coding Agent 的软件交付中，更直接的溯源对象是代码与构建链：源 commit、依赖锁文件、测试所用环境、构建步骤、产物哈希和签名、审批记录。数据水印可补充调查线索，代码签名与构建记录可证明某个产物对应哪套已记录输入和过程；两者都不能取代最小权限、隔离执行、代码审查和运行时监控。读者应先问”需要证明什么”：是某份内容的来源、某个软件包的构建历史，还是某次敏感操作由谁授权？不同问题需要不同证据。

7.9.7　怎样验证安全控制确实有效

安全评估不能只问”Agent 最后有没有完成任务”。应准备与真实仓库形态相近、但不含真实秘密的测试资料，分别放入普通说明、带有诱导文字的外部文档、变更后的工具描述、受污染的记忆条目，以及含可疑依赖变化的提交。记录三类结果：合法任务能否完成；越权动作是否被阻断；误报是否使正常任务无法推进。针对发现过的失败，将其转成回归用例，并固定 Agent、工具和策略版本，以便比较修复前后的行为。OWASP AI Agent 安全指南

如果一次测试中模型产生了危险意图，但工具网关拒绝执行，应分别记录”模型判断失败”和”执行边界成功”，以免把两者混成一个成功率。反过来，若模型这次没有受诱导，也不能由此断定边界足够安全；还需验证权限拒绝、沙箱和审计在模型失误时仍会工作。安全性最终体现为在错误输入和错误判断下，系统仍把影响限制在授权范围内。

7.9.8　小结：可信是可追溯的约束链

Coding Agent 的可信交付，始于分清用户授权和外部资料，落实到每一次工具调用的权限判断，再由代码审查、测试、构建溯源与发布审批完成闭环。提示注入、软件后门、MCP 工具投毒与记忆污染进入系统的路径不同，却都可能试图跨过”内容—指令—执行”的边界。数据水印和来源证据有助于发现与追溯问题，真正限制损害仍依赖权限、隔离与独立验证。至此，本章的四类工程技术、RSI 和安全交付连成一条可实施的路径；下一节用统一案例逐项检查这些设计。
